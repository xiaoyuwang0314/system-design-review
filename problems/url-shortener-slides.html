The product02

Two features, and four reasons people pay for them

What it does

  1. Create: take a long URL, return a short code like abc1234, store the mapping.
  2. Redirect: when someone opens short.ly/abc1234, look up the long URL and send the browser there with an HTTP redirect.

A link is created once and clicked many times. This is a read-heavy system.

Why it exists

  • Length limits: SMS, social posts, printed flyers, QR codes. Shorter URL, simpler QR code.
  • Click analytics: every click passes through the service, so it can count clicks by time, country and device. This is the main business value.
  • Change the destination later without reprinting a QR code on 100,000 boxes.
  • Branded links: amzn.to, youtu.be.

Core challenge for this problem

Generate short codes that are unique and hard to guess at scale, and serve a read-heavy redirect workload with low latency and high availability.

Step 1 · Requirements04

Ask, assume, then confirm

Functional

  1. Long URL in, unique short URL out
  2. Short URL redirects to the long URL
  3. Optional custom alias
  4. Optional expiration time

Click counts: nice to have.

Non-functional

  • Scale: 100M new URLs a day, 10 reads per write
  • Low latency on redirects
  • Availability over consistency for redirects
  • Uniqueness: never two URLs on one code
  • Durability: links last for years
  • Hard to guess: no enumerating links

Out of scope

  • User accounts
  • Editing a destination
  • Malware detection

Saying this out loud shows you control the scope on purpose.

"I'll favor availability for redirects. If redirects go down, every link ever shared breaks. A new link taking a second to show up everywhere is fine."

Step 3 · The classic follow-up06

Why 302 and not 301?

301 Moved Permanently

  1. First click: browser asks us, we answer 301.
  2. Browser caches the redirect.
  3. Every later click goes straight to the long URL. We never see it.

No click counts. And when the link expires, the browser keeps following it anyway.

302 Found (temporary)

  1. Every click comes to our server.
  2. We count it, check expiration, then redirect.
  3. The cost is more traffic, which our cache absorbs.

Click counts work. Expiration works.

"I'd use 302. A 301 gets cached by browsers, so we'd lose click counts, and expiration would stop working, because a browser that cached the redirect keeps following it."

Step 4 · High-level design07

Split reads from writes

Reads outnumber writes 10 to 1 and need higher availability, so each side scales on its own. Every box runs more than one instance: no single point of failure.

Step 4 · Request flows08

Walk through each requirement

Write flow

  1. POST /v1/urls reaches the write service by path (L7).
  2. Validate the URL, check the rate limit.
  3. Pick a code: the custom alias, or the next counter ID.
  4. Conditional write: insert only if the code is free.
  5. Return 201.

Redirect flow (cache-aside)

  1. Look up the code in Redis.
  2. Hit: check expires_at, return 302.
  3. Miss: read the database, fill the cache, redirect.
  4. Unknown code: 404, cached briefly to stop cache penetration. Expired: 410.
  5. Send a click event to the queue, asynchronously. A redirect never waits on analytics.
Step 4 · Data model09

Key-value store (DynamoDB)

Insert a row, read it by short_code. No joins, no multi-row transactions. Storage reaches hundreds of TB, and a KV store shards and replicates for us. Postgres would work at first, then need manual sharding.

Expiration in two parts

Correctness: check expires_at on every redirect. Cleanup: TTL feature or a background job, which may lag by days. Never rely on cleanup for correctness.

"I'd use a counter, since it's unique by construction. It has three weak spots: it's a bottleneck, a single point of failure, and guessable. Let me fix each one."

Deep dive · Fix 1 of 311

Bottleneck: hand out IDs in batches

server 11,000 to 1,999  (using 1,412)
server 22,000 to 2,999  (using 2,077)
server 33,000 to 3,999  (just reserved)
Rediscounter = 3,999

How it works

Each write server calls INCRBY counter 1000 once, gets a private range, and hands out IDs from memory. It returns to Redis only when the range runs out.

1,000 writes/s ÷ 1,000 per batch ≈ 1 Redis call per second.

If a server crashes, the rest of its range is never used. That's fine: we need 365 billion codes out of 3.5 trillion.

Deep dive · Fixes 2 and 312

Failover and guessability

Single point of failure

Run Redis with a replica and automatic failover. But replication is asynchronous: the new primary may have missed the last INCRBY and hand out the same range twice.

  • After failover, jump the counter forward a few million.
  • Keep the conditional write as the last safety net.

Skipping IDs is harmless.
Reusing them is not.

Guessable codes

Pass the counter through a reversible transformation with a secret key before encoding (here: multiply by a secret number, mod 627). One-to-one, so codes stay unique.

counterplain base62transformed 100000000g826Ess0E 100100000g9EqngklJ 100200000gagK64cGO

Neighbors no longer look like neighbors, so nobody can walk the list.

Wrap-up · Follow-up questions16

What the interviewer asks next

"A link goes viral at 100× traffic."

One hot key hammers one Redis node. Add a small in-process cache on each redirect server, serve redirects from a CDN or edge, and use request coalescing so an expiring entry doesn't cause a cache stampede.

"What about links to malware?"

Check new URLs against a blocklist such as Google Safe Browsing, rate limit per API key, and let us disable a code: delete it from the cache and purge the CDN.

"Users want to edit the destination."

Update the database, delete the cache key, purge the CDN, in that order. Database first, then invalidate.

"The Redis counter fails."

Fail over to the replica, jump the counter forward, and let the conditional write reject any duplicate. Servers keep serving from their current batch meanwhile.

Takeaways17

Five ideas that transfer to other problems

  1. Requirements decide the design. "Hard to guess" ruled out plain counters. "Expiration" ruled out 301.
  2. Read-heavy means cache first. Split reads from writes so each scales alone.
  3. Pick by access pattern. One key lookup, hundreds of TB: a key-value store.
  4. Name your solution's weak spots, then fix them. That is what a deep dive is.
  5. Only do math that changes a decision, and say what it decided.
